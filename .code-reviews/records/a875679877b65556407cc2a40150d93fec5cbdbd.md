### Medium (1)
- **plugins/ticketboard/lib/store.js:1823** — `runStart` refuses to start the servers when a dependency folder is still missing after setup ("Still missing after setup"). `missingDeps` treats `node_modules` as required whenever `package.json` exists, but some projects never create it (a package.json with no dependencies, tooling-only package.json in a Laravel app, Yarn PnP, pnpm with a different store layout). For those, Run app runs setup on every click and then never starts the servers. *(correctness)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `missingDeps` now requires `node_modules` only when package.json lists dependencies, and `runStart` starts the servers anyway when setup passed but a folder is still absent (Yarn PnP or another layout). It only stops when setup itself failed and the folder is still missing. Previous note: The failure path is a hard stop rather than a warning. Consider starting anyway when setup itself succeeded (r.failed is empty) and only failing when setup failed, or checking that the manifest actually lists dependencies.

### Low (2)
- **plugins/ticketboard/lib/store.js:1196** — Setup now carries on after a failed step. Setup entries are usually order-dependent (`composer install` then `php artisan key:generate` or `migrate`), so later steps run against a half-installed tree and can produce confusing errors or partial state. The change is documented, but it is applied to every step rather than only independent ones. *(correctness)*
  - status: ignored
  - dev_reasoning: Intended, the user asked for it. A stale composer.lock stopped npm install and left the app without assets. Setup steps are installs and are mostly independent. A later step that depends on a failed one fails loudly, and every failed step is listed in the log, on the ticket and in the Run app bar. Bootstrap stays re-runnable.
  - ai_reasoning: Reasonable trade-off for the stated case, but consider an opt-in per step or a profile flag, or at least stopping on steps after the first failure within the same tool group.
- **plugins/ticketboard/lib/store.js:1126** — `bootstrap` now dedupes concurrent calls per ticket and returns the in-flight promise, so a second caller's `onOutput` is dropped. A CLI `board bootstrap` or `board start` that joins a setup already started by Run app prints nothing while it waits. *(maintainability)*
  - status: fixed
  - dev_reasoning: N/A
  - ai_reasoning: Fixed. `bootstrap` now adds the later caller's `onOutput` to the running job's listeners and prints a "joining it" line. Previous note: Minor UX gap. Either attach the later caller's onOutput to the running setup or print a "joined running setup" line.
